# Conformance corpus generators

The corpora under `conformance/` are the contract both ports are held to, and every case in them is
produced by running **intlify/vue-i18n's own TypeScript**, never by hand. These are the scripts that
do the running. They live here rather than in a scratch directory so that a corpus can still be
regenerated in a year, by someone who was not there when it was first written.

| script | writes | holds |
|---|---|---|
| `generate_compile_corpus.mjs` | `conformance/compile.json` | the AST and the errors `createParser()` produces for every source in `messages.json` |
| `generate_resolve_corpus.mjs` | `conformance/resolve.json` | what `parse()`, `resolveValue()` and `resolveWithKeyValue()` make of every (object, path) pair in the script |

Both take an optional output path, which is the way to inspect a regenerated corpus before letting
it overwrite the committed one:

```sh
node generate_resolve_corpus.mjs /tmp/check.json && diff /tmp/check.json ../../conformance/resolve.json
```

## Upstream version

**`intlify/vue-i18n@12.0.0-alpha.4`.** The corpora carry it in their `upstream` field, and the
generators write that field from the clone's own `package.json`, so a regeneration against a
different version says so in the diff instead of quietly changing the contract. Regenerate only when
upstream is deliberately moved, and say so in the commit.

## Running them

```sh
git clone https://github.com/intlify/vue-i18n.git /path/to/vue-i18n   # at the version above
./bundle-upstream.sh /path/to/vue-i18n
node generate_compile_corpus.mjs
node generate_resolve_corpus.mjs
```

`bundle-upstream.sh` bundles the upstream sources into `upstream-bundle/` (git-ignored) with esbuild, which is needed
for two reasons: upstream's sources use `const enum`, which Node's built-in type stripping refuses,
and they import each other as `@intlify/*`, which resolves only through the clone's own tsconfig
`paths`. Nothing is installed in the clone — no `pnpm install`, no build of upstream's own dist.

Two things about that resolution are worth knowing before touching `bundle-upstream.sh`:

- esbuild will warn that it cannot find this repository's own `tsconfig.json` base config. It is
  harmless (that config is for `ts/`, and it needs an npm install this script does not want).
- Passing `--tsconfig` to silence the warning **breaks the build**: the flag applies one config to
  every file, upstream's `paths` stop applying, and `@intlify/shared` then resolves to whatever
  version happens to be installed in some `node_modules` up the tree — a *different* vue-i18n,
  silently. `bundle-upstream.sh` checks the bundles for that and fails instead.

Node 22 or newer, and esbuild is fetched by `npx` at a pinned version; nothing else is required.

## What is deliberately not here

The plural corpus, `conformance/plurals.json`, is generated by `scripts/generate_plural_corpus.py`
from this project's own runtime — the CLDR rules are ours by design, so there is no upstream to run.
